## 📖 章节笔记（边读边写，每章三问 + 两记）

### s01 Agent Loop — 一个循环就够了

#### 一、本章讲了什么（讲透版）

**1. 本章要解决的问题**

把"读取我目录下的文件并执行 XXX.py"这种需求丢给大模型，模型只能输出一条命令文本——它不会自己执行，也看不到执行结果，更谈不上根据结果继续推理。没有 harness 时，人被迫充当"中间层"：复制命令 → 手动执行 → 把输出粘回对话框 → 等下一条命令。每个来回都是人肉搬运。本章要做的就是把这个中间层自动化——这就是"agent"和"聊天机器人"的分水岭。

**2. 核心方案：一个循环 + 一个信号**

方案简单到出人意料：`while True`，每轮把消息历史 + 工具定义发给模型，然后检查响应这一个信号：

| 响应内容 | 含义 | 循环动作 |
|----------|------|----------|
| 含 `tool_use` 内容块 | 模型要求执行工具 | 执行 → 结果包装成 user 消息喂回 → 继续循环 |
| 不含 `tool_use` 块 | 模型认为任务完成（或只需纯文本回答） | 退出循环 |

这个设计的分工非常干净：**模型负责决策**（要不要行动、用什么行动、参数是什么），**harness 负责执行**（真正跑命令、捕获输出、回喂结果）。智能在模型侧，机制在代码侧——这正是全书"Agency 来自模型，Harness 来自工程"的最小体现。

**3. 代码走读（code.py，151 行）**

- **环境感知**：system prompt 里注入 `os.getcwd()` 和操作系统类型（Windows 下提醒模型用 cmd 语法）——agent 必须知道自己"身在何处"，这是 harness 提供 Observation 的第一课。
- **一个细节**：`os.environ.pop("ANTHROPIC_AUTH_TOKEN", None)`——用第三方网关（如我们的 Kimi 端点）时，残留的 AUTH_TOKEN 环境变量会干扰 x-api-key 认证，作者顺手排了这个坑。
- **工具定义（TOOLS）**：一个 JSON Schema——name/description/input_schema 三件套。注意：**description 是写给模型看的"使用说明书"**，模型靠它决定何时调用、怎么传参。s02 会展开这一点。
- **工具执行（run_bash）**：`subprocess.run(shell=True)` 跑命令，带了三层现实世界的防护：① 黑名单挡 `rm -rf /` 等危险命令（极简陋，s03 的权限系统才是正解）；② 120 秒超时；③ 输出截断到 50000 字符——不截断的话一个 `cat` 大文件就能把上下文撑爆（这是 s08 上下文压缩要解决的远期问题）。
- **循环本体（agent_loop）**：追加 assistant 原始响应（含所有内容块）→ 过滤出 `tool_use` 块 → 逐个执行并用 `tool_use_id` 把结果和调用配对（API 靠这个 id 对应"哪个结果回答哪个调用"）→ 结果数组作为一条 user 消息追加 → 下一轮。
- **REPL 外壳**：readline 修 macOS 中文退格乱码；`history` 列表无限增长——每一轮对话都在累积 token，这个"故意埋的雷"正是 s08 存在的理由。

**4. 本章故意缺了什么（地基上没盖的楼层）**

作者的克制是有意为之，每个"缺失"都对应后面一章：只有一个 bash 工具，读写文件靠 `cat`/`echo >` 又丑又易错（→s02）；危险命令只靠字符串黑名单（→s03 权限）；循环里没法插入日志/拦截等横切逻辑（→s04 hooks）；历史无限膨胀（→s08）；对话结束即遗忘（→s09 记忆）。"最小可用"本身就是一种教学设计。

**5. 实战观察（沙盒实测）**

在临时目录中让 agent"创建 hello.py 并运行、告诉我输出"。观察到一个超出文档描述的行为：模型**把写文件和执行合并成了一条 bash 命令**（`echo ... > hello.py && python3 hello.py`），一次 tool_use 就完成了两步——说明模型侧的"决策粒度"是灵活的，harness 的循环对此完全无感，这正是"决策归模型、执行归代码"分工的好处。随后模型输出纯文本总结，响应中无 tool_use 块，循环如期退出。

#### 二、与前后章节的关系

首章，全书地基。它定义的循环骨架（发消息→查 tool_use→执行→回喂）在后面 16 章中**始终不变**：s02 往 TOOLS 里加工具、s03 在执行前加权限判断、s04 在循环边上挂钩子、s08 在两轮之间压缩历史……所有机制都是"长在循环上"，而不是改写循环。s01 还承担了全书的破题任务：用 30 行代码证明"agent 没那么神秘"，把读者从"框架迷信"里解放出来。

#### 三、实战场景（怎么用）

1. **评估任何 agent 框架/产品**：先找到它的"循环"在哪、退出信号是什么。找不到清晰循环的，大概率是"提示词水管工"式编排。
2. **自己造轮子时**：先实现这个 30 行最小循环跑通，再按需叠加机制——不要一上来就引入重型框架，你连循环都没亲手写过就无法判断框架的取舍。
3. **排查 agent 行为异常**：理解"模型决策/harness 执行"的边界后，问题定位就有了方向——行为不合理先查模型输入（消息历史、工具描述），执行出错才查 harness 代码。

#### 五、我的问题与解答

- ❓**"循环本身始终不变"是真的吗？后面加权限/hooks/压缩时不用动循环？**
  → ✅解答（初步，读到对应章节后回来验证）：从章节标题推测作者的解法——权限（s03）应该包在"工具执行"这一步的外面而不是循环结构上；hooks（s04）的标题直接写了"挂在循环上，不写进循环里"；压缩（s08）应该是两轮之间替换 history 的内容而非改循环逻辑。即：**机制注入点是"循环的边缘"，循环骨架不动**。待 s03/s04/s08 验证。
- ❓**模型怎么"知道"该停止调工具？stop_reason 和 tool_use 块是什么关系？**
  → ✅解答（基于 API 常识，已查证方向）：API 响应带 `stop_reason` 字段——`tool_use` 表示"我停是因为要调工具"，`end_turn` 表示"我说完了"。本章代码没看 stop_reason，而是直接查内容块里有没有 tool_use，两种判断在实践中等价，但内容块判断更稳健：模型可能同时输出文本块+tool_use 块（边解释边行动），此时 stop_reason 是 tool_use，内容块判断同样能抓到。反过来如果用 stop_reason 判断，也能工作。结论：退出条件本质是"模型本轮没有请求任何行动"。

#### 八、📚 本章拓展资料与对照（每条结合本章展开）

**1. ReAct 论文（Yao et al., arXiv:2210.03629, ICLR 2023）——学术源头**

这篇论文讲了什么：2022 年 Google Brain 与普林斯顿的工作。当时 LLM 的"推理"（思维链 CoT，纯内部推演，容易幻觉）和"行动"（生成动作计划，没有推理串联）是分开研究的。ReAct 的做法是让模型**交替生成 Thought（推理轨迹）→ Action（行动）→ Observation（环境反馈）的三元组**，用 few-shot 提示引导。推理帮模型制定/跟踪/修正计划、处理异常；行动的结果反过来 grounding 推理，减少幻觉。在知识问答（HotpotQA/FEVER）和交互决策（ALFWorld 文字游戏、WebShop 网购模拟）上都超过了纯行动或纯推理路线。

与本章的对照：本章的循环就是 ReAct 的工程落地——对应关系：Action = 响应里的 `tool_use` 块，Observation = 回喂的 `tool_result` 消息。**关键差异在 Thought**：ReAct 时代模型需要 few-shot 提示才能"显式说出"思考过程；本章的循环里根本没有 Thought 通道，因为 2024 年后的模型把工具使用和推理直接训进了权重，思考在模型内部完成（或以后台 thinking 块存在）。从 ReAct 到本章，能看到三年间"提示词技巧内化为模型能力"的演进——这恰好印证全书核心观点：agency 是训练出来的，越来越不需要代码侧的诱导。

**2. Anthropic《Building Effective Agents》（2024-12-19，Erik Schluntz & Barry Zhang）——赞同，但更冷静**

这篇博客讲了什么：Anthropic 总结了与数十个行业团队共建 agent 的经验。核心结论："最成功的实现都在用**简单、可组合的模式**，而不是复杂框架。"它给出两个关键定义：**workflow** = LLM 和工具通过预定义代码路径编排；**agent** = LLM 动态指挥自己的流程和工具使用。然后把 agentic 系统从简单到复杂排了个光谱：augmented LLM（模型+检索+工具+记忆，基本积木）→ 五种 workflow 模式（提示链/路由/并行/orchestrator-workers/评估器-优化器）→ 自主 agent。对自主 agent 的适用条件说得很克制：只用于"步骤数无法预测、无法硬编码固定路径"的开放问题，且要接受用成本和延迟换效果。文末还强调工具设计（他们叫 ACI，agent-computer interface）要和人机界面一样用心。

与本章的对照：本章的 30 行循环就是文中"自主 agent"的最小实现，TOOLS 就是 augmented LLM 的"augmentation"。文章为本书的反框架立场提供了**官方背书**。分歧在语气与边界：本书把编排派叫"提示词水管工"、说"一个循环就够了"；Anthropic 则明确给 workflow 留了正当位置——任务流程可预测时，workflow 更省钱、更可控、更好审计。立场差异的根源：本书是教学+布道（先把本质讲透），Anthropic 要面对生产客户的合规与成本约束。

**3. OpenAI《A Practical Guide to Building Agents》（2025）——赞同，互补在"何时该用"**

这份指南讲了什么：同样把 agent 定义为"模型 + 指令 + 工具"在循环中运行直到任务完成。它最有价值的部分是本书没讲的**决策标准**：什么时候值得上 agent？三个信号——决策规则复杂到难以维护、依赖非结构化数据理解、现有规则系统维护成本爆炸。工程路径上主张：先做单个能力扎实的 agent，撑不住了再拆多 agent（manager 模式）；guardrails（护栏）要分层叠加。

与本章的对照：对"循环是核心"完全一致。互补点：本章教你"怎么造"，这份指南教你"什么时候该造、什么时候别造"——两者合起来才是完整视角。

**4. LangGraph（LangChain 阵营）——反方，必须正面回答**

LangGraph 的主张：把 agent 表示为**显式状态图**——节点是步骤（LLM 调用、工具执行），边是控制流（含条件分支和回边），状态是显式共享对象。它的卖点恰好是裸循环的软肋：checkpoint 持久化（崩溃可恢复）、人在回路中断（关键节点等人审批）、可观测性（每一步状态可见可回放）、精细控制（强制某分支必须走）。

与本章的冲突：本章说"一个循环就够了"，LangGraph 说裸 while 循环上不了生产。我的辩证判断：**"循环"和"图"不是替代关系，而是抽象层级关系**——LangGraph 图里那条"工具执行完回到 LLM 节点"的条件回边，本质就是本章的 agent loop；图 = 循环 + 显式状态管理 + 控制点。学原理时，循环视角直击本质（本书对）；上生产时，持久化/审批/审计是真实需求（LangGraph 对）。**最有趣的伏笔**：本书 s16 的标题是"模型决定单步，脚本决定编排"——作者自己最终也承认编排有其位置。读到 s16 时必须回来验证：本章的激进是不是一种"先破后立"的教学策略。

**辩证总结**：学本质用循环视角，上生产加状态管理；反框架不等于反工程。四份资料读完，本章那 30 行代码的分量反而更清楚了——它是整个行业共识的最小公约数。
